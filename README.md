## Artemis Financial Vulnerability Assessment

For this project, I worked with Artemis Financial, a financial consulting company that creates savings, retirement, investment, and insurance plans for its clients. Because the company handles financial information, it needed to make sure its software protected sensitive data and used secure communication. My job was to review the application for security weaknesses and recommend changes that would make it safer as the software was modernized.

One part I did well was looking at the application from more than one security angle instead of relying only on an automated scan. During my manual review, I found problems such as hardcoded database credentials, the use of a root database account, unvalidated user input, exposed stack traces, missing authentication and authorization controls, and weak encapsulation of financial data. I also found outdated dependencies that introduced known vulnerabilities. This showed me why secure coding needs to be part of development from the beginning. A security problem can affect customer information, the reliability of the application, and the company's reputation.

The most helpful part of the vulnerability assessment was comparing my manual review with the OWASP Dependency Check results. Manually reviewing the code helped me find problems with how the application was written, while dependency scanning found vulnerabilities inside libraries that might not be obvious from reading the source code. The scan found vulnerable components such as Bouncy Castle, Spring Framework, SnakeYAML, Jackson, Log4j, Logback, Hibernate Validator, and Tomcat. Seeing both types of results helped me understand why one security testing method is not enough.

I increased the layers of security by recommending several changes instead of depending on a single solution. These included removing hardcoded credentials, using a database account with limited permissions, validating user input, adding authentication and authorization, protecting financial fields through encapsulation, improving error handling, and updating vulnerable dependencies. In future projects, I would continue using manual code reviews along with tools such as OWASP Dependency Check. I would also use CVE and CVSS information to understand the seriousness of a vulnerability before deciding which problems need to be fixed first.

To make sure the application remained functional and secure, I would test the application after making security changes rather than assuming a change worked correctly. I would verify that the expected functionality still worked, repeat the manual code review, and run the dependency scan again. This is important because fixing one problem can sometimes introduce another problem or add a new dependency. Security testing should continue as the application changes instead of being something that is only done once.

Some of the most useful resources and practices from this course were OWASP Dependency Check, vulnerability reports, CVE information, manual code review, input validation, least privilege, secure error handling, cryptography, and dependency management. I can use these same practices in future programming assignments because they apply to more than just financial software. I also have a better understanding now of why developers need to pay attention to the libraries and frameworks their applications depend on, not just the code they personally write.

If I were showing this project to a future employer, I would use my Artemis Financial Vulnerability Assessment Report as an example of my ability to look at software from a security perspective. It shows that I can inspect code for vulnerabilities, use automated security tools, interpret vulnerability results, and recommend realistic ways to reduce security risks. More importantly, it shows that I understand secure software development as part of the development process rather than something that gets added after an application is finished.
